# Windows 11 23H2 compatibility validation

The Windows 11 minimum is now 23H2. Windows Server remains 2025 or later.
This change was developed and exercised on Windows 11 Enterprise 23H2,
build 22631.7517. A newer Windows host was not available for a fresh run.

## Implementation

- `ReleasePseudoConsole` is resolved dynamically. The executable imports
  Create/Close/ResizePseudoConsole, but not ReleasePseudoConsole, so the
  loader can start it on 23H2.
- 24H2 and later retain the existing release/asynchronous-close path.
- 23H2 reserves independent close and output-drain workers before creating
  each console. Natural close waits for the whole supervised job, preserves
  the final output for the caller, and rejects resize once close can begin.
- Explicit close cancels pending I/O before transferring the output pipe.
  Separate completion events support shutdown after the event loop stops.
  Pending packets are orphaned before Lua finalizers can pump the loop again.
  Native drain reads suppress IOCP notification and never access Lua or the
  child's state. Both workers are joined before the process exits.
- Full sanitizer validation also exposed a pre-existing use after free in
  the JSON duplicate-key diagnostic. The diagnostic is now formatted while
  the yyjson document still owns the key. Its existing check verifies the
  reported key as well as the error code.

## Verification

- Final production suite: **1,044 checks passed**.
- One preceding full run failed the existing 31-process-chain shape
  assertion (`#node.children <= 1`). The isolated process suite then passed
  all **82 checks**, and the complete suite was confirmed again. This was
  not attributed to the compatibility change or an external cause.
- Final console regressions under AddressSanitizer: **47 checks passed**.
- Complete sanitizer suite before the final resize guard: 1,042 passed and
  one memory-file concurrency check failed with Windows error 5; there was
  no sanitizer memory-error report. That isolated memory case subsequently
  passed all **19 checks**. The entire sanitizer gate is therefore recorded
  as having encountered a failure, rather than relabeled as a clean run.
- GCC native static analysis passed.
- Parser fuzzing passed all three 10,000-case seeds for the command-line,
  duration, date, path, CSV, INI, JSON and registry parsers. The last change
  after this run is the console resize guard and its regression.
- The 60-second soak completed 38 rounds in 61 seconds with handle growth
  -3 and private-memory growth +4.2 MiB, but **21 state-file writes failed**.
  A separate 1,000-write comparison reproduced the same `FS access` /
  Windows error 5 in the original 0.6 executable (4 failures) and this
  compatibility work (3 failures). The cause remains unisolated; see
  [the existing file-access finding](../docs/shortcomings.md#intermittent-access-denied-while-replacing-files).
