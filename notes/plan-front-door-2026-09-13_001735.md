# Plan: kuu as the front door

Written 2026-09-13 after a whole-project review on 2026-09-12 and the
decisions that followed it. This supersedes the direction recorded in
`design-js-capability-2026-09-12_155114.md`, which stands as the record of
what was considered; nothing in it is built and nothing in it will be built
as written.

## The decision

kuu is the front door of a project. Everything that *runs* in a project runs
through `kuu.exe`: a task, a build, a test, a tool, a fetch, anything that
spawns or reaches out. Writing code is not a crossing: an agent edits with
its own hands, and what it wrote becomes the door's business the moment it
first runs — `check` stands at that threshold. What passes through the door gets
a job, a deadline, limits, tree-kill on the door's death, a record, and where
the door can read it, a check. If a project needs something the door cannot
do, the project builds a tool for it — in whatever technology the agent
writes best — fetches or builds it by hash into its own root, and calls it
through the door.

The door itself is Lua on C, small, and built with great care, because it is
the only thing in this arrangement that must last fifteen years. It stops
growing.

The project's own orchestration stays where it is and in what it is: setup,
prerequisites by URL and hash, build, test, the tasks and their
dependencies, declared in `manifest.lua`, in Lua, checked by `check`, run by
`kuu run` — exactly as Time Actual does it today. "Any technology" applies
to the tools a task calls, never to the tasks. A tool's I/O is declared in
the same file, beside the tasks that call it; that declaration replaces no
task and gates nothing at run time.

There are exactly two kinds of thing a program can reach, each with one owner
and one authored description: the palette, kuu's, shipped in the executable,
described by `_palette`, gated by `require`; and the project's tools, the
project's, in `.tools/`, declared in `manifest.lua`, called through the door.
There is no third kind. kuu is never extended; a project is. A tool that
wants to read like a module is wrapped by an ordinary project module that
calls it through the door, and `check` reads both. `.kuu/` holds kuu's own
state — the notebook, the ledger — and never anything that runs. A thing
enters the palette only when it cannot be a tool, which the door makes rare. What it gains from here is what a door needs: a way to know the
tools it opens for, a memory of what passed, and later an eye on what went
around it.

What it is not, decided this week and not to be revisited without new
evidence:

- Not a language, and not a compiler (2026-09-11).
- Not a coordinator, and not coordinated. Every project stands fully alone;
  nothing outside a project's root acts on it (2026-09-12).
- Not the owner of a second runtime. No JavaScript, Go, Tcl or any other
  runtime is mandated, shipped, fetched by kuu, or given a place in the
  manual. A project that wants a confined tool chooses its own technology;
  the manual says what a confined tool must provide, not what to write it in
  (2026-09-13).
- Not frozen. The 1.0 criteria stand — a month of use, a cold adopter, a
  clean soak on every host — and none is met. No release is tagged until the
  front-door work below has landed, and 0.10.0 is that release.

## Decisions taken 2026-09-13

| question | decision |
|---|---|
| the provisional modules `svc`, `evt`, `sys.signature`, `pty` | kept, provisional; not removed |
| where a tool's I/O is declared | in `manifest.lua`, as `tool "name" { ... }` beside `task "name" { ... }`; no separate file. `check` reads the declaration as a literal without executing; `run`, `list` and `capabilities` execute it; a test holds the two readings equal |
| where the ledger lives | `.kuu/ledger/`, local to the machine, gitignored, rotated |
| what ships next | 0.10.0, held until the front door lands; Time Actual stays on 0.9.0 |
| recommended tools or runtimes | none; the confined-tool page is technology-neutral |
| the name of the project's declaration file | `manifest.lua`; `tasks.lua` still found for one release, with a warning |
| tools that extend kuu versus tools of the project | no distinction: the palette is kuu's, everything else is the project's tool; kuu is never extended, and `.kuu/` never holds anything that runs |
| NDJSON | kuu's own output format, everywhere kuu reports, and `kuu run --json` becomes a stream; for a tool the project writes it is recommended with a reason, never required; a fetched tool is called and described as it is |

## Phase 1 — take great care with the C

The gate:

- `make asan` runs inside `make gate`. Today it is described as required and
  is not run; `build/kuu-asan.exe` was 22 commits stale on 2026-09-12.
- The production compiler is pinned by hash into `.tools`, the way the test
  Clang already is. Today `ucrt64` is one robocopy of the owner's MSYS2 on
  one disk, and gcc 16.1.0 is the only compiler that has ever built kuu
  under `-Werror`.
- The `check` corpus gains generated Lua, so a shape like `cfg.paths.build`
  or a constructor-built module is found by the gate and not by a consumer.
- Eleven exported names are never called in the suite, `check.exports` among
  them; every public name gets at least one success-path call.

Confirmed defects, from the review of 2026-09-12:

- `fs.rename` and `fs.copy` make one attempt where `fs.write` retries; the
  intermittent FS failures are this, not flakiness (`src/fs.c:728`, `:749`).
- A program file or a `require` root beyond 260 characters fails at the
  entry route while `fs.read` of the same path succeeds (`src/program.c`,
  `src/state.c:243-253`).
- Error messages are cut at 1023 bytes (`src/err.c`, `char message[1024]`),
  so a long-path failure loses its Windows reason.
- `proc.tree`'s 31-process chain check is an open intermittent; it is
  isolated, not tolerated.
- `http`'s download rename has no retry; the job-message ordering assumption
  at `src/proc.c:666` is either proven or defended; the raise-path byte leaks
  in `src/fs.c` are closed.

The two laws, in every module:

- An unknown option raises `usage`. Eleven option-taking calls in eight
  modules accept one silently today (`fs.dirs`, `fs.glob`, `hash.sum`,
  `hash.file`, `text.tobase64`, `time.iso`, `archive.list`, `ini.encode`,
  `csv.encode`, `csv.decode`, `json.encode`); four raise `badvalue` for it
  (`evt.read`, `sys.signature`, `task.defaults`, `cli` specs).
- An expected failure returns `nil, err` and a mistake raises, as `err.md`
  says, in the six domains that currently do both — a non-UTF-8 subject
  raises in `re` and returns in `text`; the same refused path raises in `fs`
  and `http` and returns in `hash`; `time.duration` raises where
  `cli.duration` returns bare nil.

Then the Win32 surface is counted — about 180 functions today plus the
undocumented `archiveint.dll`, `NtQueryInformationProcess` and
`RtlGetVersion` — and the count is recorded, so that "small" is a number.

## Phase 2 — the front-door contract

The file at the door is `manifest.lua`. `project.TASKS_FILE` and everything
that names it — `project.find`, `kuu run`, `kuu list`, `capabilities`,
`check`'s root rule, the manual, the cookbook, kuu-test-project — move to the
new name; a root with only `tasks.lua` is still found for one release and
reported with a warning, so Time Actual renames when it upgrades and not
before. Nothing inside the file changes: `task "build" { ... }` reads as it
did, and `tool "name" { ... }` joins it.

`docs/tools.md`, the contract a tool is called under, in any language:

- The door gives every tool a job, a deadline, limits, a working directory
  and nothing on `PATH` it did not fetch itself, and reads its exit code and
  its streams. That is the whole contract for a fetched tool — `git`,
  `signtool`, a compiler — which the door calls as it is and declares in
  the manifest as it is. kuu imposes no format on a tool's output; the
  declaration says what shape it produces and the task reads that shape.
- For a tool the project writes, the page recommends one shape, for a
  measured reason and not as a rule: NDJSON on stdout, one complete record
  per line, so a tool killed at its deadline leaves a readable prefix rather
  than a truncated document, and kuu's stream reads already deliver lines
  with backpressure. Arguments arrive as argv or as one JSON object on stdin,
  whichever the manifest says; diagnostics on stderr; non-zero exit on
  failure. Time Actual's tools are the worked example.
- kuu owns exactly one wire: its own output. Every `--json` verb and the
  ledger speak NDJSON, and `kuu run --json` becomes a stream of events —
  task started, child started, child finished, task finished, one line each
  — rather than one envelope at the end, which is what a manager or a
  harness watching a long task needs. kuu speaks to whoever called it; it
  never reads a tool's protocol, and no tool needs to know kuu's.
- The page also shows the one pattern for making a tool read like a module:
  `tools/yaml.lua` exporting `decode` and calling the tool through the door.
  It is an ordinary project module — `check` reads its exports from its text
  and its calls against the manifest's `tool` declaration — so that no agent
  invents a plugin system where none is needed.

A tool is declared in `manifest.lua` beside the tasks that call it, in the
same shape a task is. A draft, to be settled when the first project writes
one:

```lua
tool "report" {
  exe     = "tools/report/report.exe",
  args    = { ["--out"] = "path", ["--since"] = "string" },
  output  = "ndjson",
  emits   = { "rows", "path" },
  timeout = "5m",
  reach   = { read = { "src", "build" }, write = { "build" }, net = {} },
}

tool "signtool" {
  exe    = ".tools/sdk/signtool.exe",
  args   = { sign = "flag", ["/sha1"] = "string", ["/tr"] = "string" },
  output = "lines",
}
```

- The declaration is read two ways from one source. `kuu run`, `kuu list`
  and `capabilities` execute the manifest, as they do for tasks today.
  `check` reads it as a literal, without executing anything, the way it
  already reads a module's `M.name =` shapes: a computed key or an expression
  where a literal belongs puts that tool out of reach, and the report says
  so. A suite case holds the executed and the scanned readings equal, so
  they cannot drift. This is not the inference the inheritance law forbids
  — the declaration *is* the authored manifest; only its syntax is Lua.
- The call side is `task.exec { tool = "signtool", ... }`: `exe` and
  `timeout` resolve from the declaration, and `check` verifies the arguments
  against `args`. A call through the door with an argument the declaration
  does not name is a finding of the same kind as a palette name. A tool run
  with no declaration is a warning — coverage, not bypass.
- `emits` is descriptive. `check` does not follow a value through
  `json.decode`, so a result field the tool never produces is caught only
  where the wrapper-module pattern is used and the wrapper's exports are read
  as a module. `capabilities` lists `emits`; the manual says which of the two
  `check` verifies, rather than implying both.
- `capabilities` lists the project's tools from it, which is the half of
  "what is available here" it could not answer before.
- `reach` is declared and shown; whether it is enforced depends on the tool's
  own technology. The door records it and does not pretend to enforce it.

`docs/confined.md`, technology-neutral: what a confined tool must provide —
a permission model that refuses by default and fails rather than prompts;
no ability to spawn, so the door's lifetime law is not bypassed one level
down; dependencies vendored into the repository and pinned, never fetched at
run time; and the one Windows fact the spike of 2026-09-12 established for
any lexical path sandbox: a junction inside a granted directory walks out of
it, and neither allow nor deny lists see it. So the door supplies the
preflight: an `fs` function that reports the reparse points under a
directory, for a project to call before granting one. The spike's figures —
startup, footprint, round trip — are evidence in this note's neighbour and
name no runtime in the manual.

The sentence, in `index.md`, `kuu.md` Part I, and `capabilities`' own
output: everything that runs in this project runs through `kuu.exe`; if
something cannot, build a tool and call it through the door. Editing is
yours; running is the door's.

## Phase 3 — the ledger

The door remembers what passes through it, written from what it observed
and never from what a tool reported.

- One atomic-append primitive in C. Records in `.kuu/ledger/<day>.ndjson`,
  gitignored, rotated by age; schema versioned from the first line.
- One record per crossing — a verb, a task, or a manifested tool: `v`, start
  and end, kind and name, argv, cwd, status, exit code, bytes on each stream,
  kuu's version, git `HEAD` and dirty state at entry and exit, and the tree
  delta since the previous crossing (a walk with the prune list, sizes and
  mtimes, content hashed only for what moved). That delta is mostly edits,
  and that is its purpose: it says which changes this run ran against. An
  edit with no crossing after it is work in progress, not a bypass.
- Each record carries the hash of the previous, so an edited line is
  detectable. Nothing prevents editing; the chain makes it visible.
- `capabilities` shows the last crossings and the count of changes no
  crossing accounts for, which is zero until the watcher exists.

## Phase 4 — the record generates itself

- Part I's figures, `--help`, verb and page counts are produced by the
  bundler from the executable and held by a test. Every wrong figure found
  on 2026-09-12 was one a hand wrote and nothing generated.
- `_palette` is authored for the nineteen modules it describes by name only,
  so "an option the call does not take" holds for every call.

## Phase 5 — later, when something runs unattended

- `kuu watch`: a resident door that watches the root, with `fs.watch`'s
  overflow reported rather than hidden. Its signal is narrow on purpose:
  a change in a place only a run should change — `build/`, `dist/`,
  `.tools/`, `.kuu/` — with no crossing to account for it, and a process
  running from under the project root that the door did not start, which
  `proc.list` sees. Source edits are never flagged; they are the agent's
  hands, not a bypass.

## After, and not kuu's work

The first management program on the door, in FlowNet, in whatever it is
written in, called through `kuu run`. The month of use starts when it runs.
The cold adopter. Then, from evidence, whether anything wants freezing.

## Out

A coordinator. A language. A mandated or recommended runtime. Any new palette
module before a project's tool has proved it cannot be a tool. A freeze
before the criteria hold. Tcl.

## Defaults I have taken, changeable without ceremony

- `check` warns, never errors, on a tool run without a manifest.
- The ledger keeps ninety days locally; summaries a project wants to keep
  are committed by the project, not by the door.
- The tree delta uses sizes and mtimes and hashes only what moved; a full
  content hash is a flag.
- A `tool` declaration is read by `check` and `capabilities` and resolved by
  `task.exec { tool = ... }`; `task.exec` with a plain program still runs it
  without a declaration, so nothing existing breaks.
