# Handoff: build 0.7, the last capabilities before the freeze

Written 2026-09-10 for the agent that continues kuu. Everything below is
decided; the owner wants all of it built and released as 0.7. Nothing is
frozen yet, so shape the new APIs well rather than cautiously, but change
existing contracts only where the consistency pass below says so.

Read first, in this order: `docs/roadmap.md` (decisions, inventory,
milestones, the Lua-versus-Tcl ledger), `docs/shortcomings.md` (what real
use found), `docs/adopting.md`, `docs/proc.md`, and `src/loop.h` (the
runtime's invariants). Then `git log --oneline -40`.

## The rules of the house

These are the owner's decisions. Do not re-open them, do not build evidence
for the alternative, do not offer them as poll options.

- kuu is a Lua 5.5 runtime for agents on Windows: one static executable, a C
  host, PUC Lua, a native palette. Windows 11 25H2 and later and the
  equivalent Server releases only; no fallbacks for older Windows.
- The compiler is the MSYS2 UCRT64 gcc copied into `.tools`; the build is
  GNU make with cmd recipes. kuu never builds or bootstraps itself. No
  PowerShell anywhere in the repository. Not Zig, not MSVC, not Rust.
- Every project carries its own `kuu.exe` directly in its repository root,
  gitignored, copied by hand from a release. Nothing on `PATH`, no machine
  changes, no bootstrap scripts, no `kuu init`, no shared tool caches.
  Projects fetch prerequisites by url and sha256 into their own `.tools`.
- kuu's own repository stays free of kuu: no `tasks.lua` there.
- Versions are Major.Minor natural numbers; no patch, no suffix.
- Report plainly, in the ledger, wherever Lua proves weaker than Tcl.
- Findings from real repositories go in `docs/shortcomings.md`, with the
  trigger, the impact, the workaround, and the status.
- `docs/*.md` is embedded in the executable as the manual. Process notes
  like this one live in `notes/`, never in `docs/`.
- The owner works from more than one machine and hands over through dated
  notes like this one. Fetch before you start.

Idioms every new module follows; read one existing module of each kind
before writing:

- A C module is `src/<name>.c` with `int ku_open_<name>(lua_State *L)`,
  declared in `src/state.h`, registered in `package.preload` in
  `src/state.c`. A module with a Lua half uses `open_hybrid` with a chunk
  under `lua/<name>/` (see `net`, `sync`, `fs`).
- Errors are `{domain, code, message}` tables: `ku_err_fail` for `nil, err`,
  `ku_err_raise` for programming mistakes. Each module's codes are a closed
  set listed at the end of its manual page.
- A native call that must wait parks the coroutine with `ku_wait` and is
  woken by the loop (`src/loop.h`); it never blocks the thread. Foreign
  threads may only `ku_loop_post`.
- Native memory that must survive a raise belongs to the stack through
  `ku_hold_new` and `lua_toclose` (`src/hold.h`); check every argument
  before allocating anything.
- Strings from Lua that reach a NUL-terminated API go through
  `ku_check_cstring`; durations and sizes through `ku_check_duration` and
  `ku_check_bytes`; paths through `ku_wpath_make`.
- Every module has a page in `docs/`, a row in `docs/index.md`, rows in
  `docs/powershell.md` mapping the cmdlets it replaces, and a case in
  `test/cases/<name>.lua` listed in `test/run.lua`.
- Commit per feature with the suite, the analyzer, and `kuu check` green;
  push to main.

## The features

### 1. `proc` limits on children

Option on `proc.run`, `proc.start`, and `task.exec`:

```lua
proc.run { "build.exe", limits = { memory = "512M", cpu = "30s", processes = 8 } }
```

`memory` is the job-wide commit limit (`JOB_OBJECT_LIMIT_JOB_MEMORY`), `cpu`
the job-wide user-mode time (`JOB_OBJECT_LIMIT_JOB_TIME`), `processes` the
active process count (`JOB_OBJECT_LIMIT_ACTIVE_PROCESS`), all set with
`JOBOBJECT_EXTENDED_LIMIT_INFORMATION` on the job every child is already
born into (`src/launch.c`, `src/proc.c`). The job's completion port already
delivers messages to `on_job` in the loop (`KU_SRC_JOB`): handle
`JOB_OBJECT_MSG_END_OF_JOB_TIME`, `JOB_OBJECT_MSG_JOB_MEMORY_LIMIT`, and
`JOB_OBJECT_MSG_ACTIVE_PROCESS_LIMIT`. On a memory or process breach kuu
terminates the job itself, so the behaviour is uniform; the kernel already
terminates on the time breach. The result reports `status = "limit"` and
`limit = "memory" | "cpu" | "processes"`. Bad values raise PROC badvalue.
Tests: a child that allocates a gigabyte under `memory = "64M"`, a busy loop
under `cpu = "1s"`, a `cmd.exe` fan-out under `processes = 2`; each ends
with the right `limit` inside a few seconds and leaves no survivor. Manual:
a "Limits" section in `docs/proc.md`, and `docs/task.md` for `task.exec`.

### 2. Deadlines: `sched.deadline` and `task.defaults`

```lua
local ok, e = sched.deadline("30s", function()
  local r = assert(proc.run { "slow.exe" })
  http.get(url)
end)
```

`sched.deadline(duration, fn, ...)` runs `fn` and returns its results, or
`nil, SCHED deadline` when the deadline passes while `fn` is waiting on the
loop. Design: a C primitive registers the running coroutine's innermost
deadline in a registry table keyed by the thread; `ku_wait` consults it and
arms the waiter's timer for the sooner of the call's own timeout and the
deadline; when the deadline fires, the push raises a `SCHED deadline` error
carrying a token. The Lua half wraps `fn` in `pcall` (pcall is yieldable),
clears the deadline, and re-raises any error whose token is not its own,
so nested deadlines compose and the innermost soonest wins. A deadline
cannot interrupt a script that computes without waiting; say so in the
manual. Children started inside stay alive; the caller decides, usually
with `<close>`. Tests: a deadline around `sched.sleep`, around
`proc.run`, nested deadlines both ways, a deadline that is not hit
returning results unchanged, a raise inside `fn` passing through.

`task.defaults { timeout = "10m" }` in `tasks.lua` gives `task.exec` a
default deadline; Time Actual wrapped every call to add exactly this.
Only `timeout` for now; refuse unknown keys with TASK badvalue.

### 3. `svc`: the Service Control Manager

```lua
svc.list()                      -- { { name, display, state, start, pid }, ... } sorted by name
svc.status("Dnscache")          -- { name, display, state, start, pid, exe } | nil, SVC notfound
svc.start(name [, timeout])     -- true | nil, err     waits for "running"
svc.stop(name [, timeout])      -- true | nil, err     waits for "stopped"
svc.restart(name [, timeout])
svc.wait(name, state, timeout)  -- true | nil, SVC timeout
```

States: `running`, `stopped`, `start_pending`, `stop_pending`, `paused`,
`pause_pending`, `continue_pending`. `start` is `auto`, `manual`,
`disabled`, or `boot`, `system`. C primitives on `OpenSCManagerW`,
`EnumServicesStatusExW`, `QueryServiceStatusEx`, `QueryServiceConfigW`,
`StartServiceW`, `ControlService`; the waiting in a Lua half that polls
`status` with `sched.sleep`, so the loop keeps running. Without elevation a
change answers `nil, SVC access` naming the service; never a silent
no-op. Codes: notfound, access, timeout, badvalue, oserror. Tests: `list`
contains `EventLog`; `status "Dnscache"` is running with a pid; `stop` on
a protected service without elevation is SVC access; an unknown name is
notfound; `wait` for a state already held returns at once. Manual page,
and `Get-Service`, `Start-Service`, `Stop-Service` rows in the map.

### 4. `check` learns the palette's names

`kuu check` already resolves `require` literals (`lua/check.lua`). Extend
it: for a local bound to a kuu module, `local fs = require "fs"`, every
`fs.<name>` field access must name an export, else an error: `fs.exist is
not a name in fs; did you mean fs.exists?`. Exports come from requiring
kuu's own modules inside the checker and reading their tables, which is
safe because they are kuu's; project modules are not checked. Skip dynamic
access such as `fs[name]`. The scan must skip strings and comments; reuse
or extend the tokenizer the require resolution uses. Tests in
`test/cases/check.lua`: a wrong name is an error with the suggestion, a
right name is silent, a project module is left alone, the JSON report
carries the new kind.

### 5. `sys.signature`

```lua
sys.signature(path)  -- { signed = true, valid = true, signer, issuer, thumbprint, timestamped }
                     -- { signed = true, valid = false, reason = "expired" | "untrusted" | "tampered" | ... }
                     -- { signed = false }  |  nil, SYS notfound
```

`WinVerifyTrust` with `WINTRUST_ACTION_GENERIC_VERIFY_V2` and
`WTD_CHOICE_FILE`, revocation off unless `{ revocation = true }` is given,
then `CryptQueryObject` and `CertGetNameStringW` for the signer and
issuer, the certificate's SHA-1 for `thumbprint`, and the presence of a
countersignature or RFC 3161 attribute for `timestamped`. Embedded
signatures only: Windows' own catalog-signed files report
`signed = false`, and the manual says so. Map `TRUST_E_*` and `CERT_E_*`
results to the `reason` words. Tests: `http_fixture.exe` is unsigned; if
`rt.exe` is signed (the release binary is), the signer contains
"Vincent Vercauteren"; a copy of a signed file with one byte changed is
`valid = false, reason = "tampered"`; a missing path is SYS notfound.

### 6. `evt`: the event logs

```lua
evt.read("System", { since = time.now() - 86400, level = "error", limit = 200, provider = "Service Control Manager" })
-- { { time, level, id, provider, message, record, computer }, ... } newest first
evt.logs()  -- the channel names
```

`EvtQuery` on `wevtapi.dll` with an XPath built from the options,
`EvtNext` in batches, `EvtRender` for the system fields, and
`EvtFormatMessage` for the message with a fallback to the raw event XML
when the publisher metadata is missing. Levels: `critical`, `error`,
`warning`, `information`, `verbose`. Read-only; `Security` needs
privilege and answers `nil, EVT access`. Codes: notfound (channel), access,
badvalue, oserror. Bound the work: `limit` defaults to 1000 and caps at
100000; render lazily if it proves slow. Tests: `System` since a day ago
returns a table whose entries carry typed fields; an unknown channel is
notfound; `logs()` contains `Application` and `System`; the filter by
level holds. Manual page, and `Get-WinEvent` in the map.

### 7. `pty` with `expect`, provisional

```lua
local p <close> = pty.spawn { "cmd.exe", cols = 120, rows = 30, cwd = ..., env = ... }
p:expect({ ">" }, "5s")              -- the prompt; patterns are Lua patterns
p:write("echo hello\r")
local text, which = p:expect({ "hello", "error" }, "5s")
p:read("1s")                        -- raw bytes, VT sequences included
p:text()                            -- the plain text seen so far
p:resize(80, 24)
p:wait("10s"); p:kill()
```

`CreatePseudoConsole` with `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`, the
child born into a kill-on-close job like every other child, the console
pipes created as named pipes with `FILE_FLAG_OVERLAPPED` and attached to
the loop, so reads are `ku_io` requests and `expect` is a waiter that the
arriving bytes wake. `text()` is a plain-text view produced by a small VT
filter: CSI and OSC sequences dropped, CR, LF, and backspace applied, no
cursor addressing, no screen model; say exactly that in the manual and mark
the module provisional, outside the future freeze. The `conhost.exe` the
system starts appears in `proc.tree`; document it. Tests: drive `cmd.exe`:
expect the prompt, run `echo`, expect the output; `set /p name=Enter:` reads
from the console and answers what was written, which a pipe could not do;
`expect` timeout is PTY timeout and leaves the child alive; `<close>` kills
the tree. This is the largest item; do it last, and give it the most
adversarial tests.

## The requirements that are not features

- **An API consistency pass.** Before the release, walk every module page
  and its source: option names are `timeout`, `maxout`, `cwd`, `env`,
  `limits` everywhere they apply; every module lists its complete, closed
  error-code set; the `--json` outputs of `run`, `list`, and `check` are
  documented as schemas in `docs/task.md` and `docs/check.md`; anything
  inconsistent is changed now, recorded in `docs/upgrading-0.7.md` with
  the 0.6 form beside the new one.
- **A stability statement,** `docs/stability.md`: which modules and verbs
  will be frozen at 1.0, what a 1.x may add, what it may never change, how
  a `tasks.lua` should guard its version from now on (a minimum, not an
  equality), and that `pty` is provisional.
- **A cookbook,** `docs/cookbook.md`: the ten things agents do most, each a
  complete short program: wait for a port to open, install a tool by hash,
  tail a log while a build runs, find the process on a port and stop it,
  verify an installer's signature before running it, check a service and
  start it, read the last errors from the event log, run a step under a
  deadline with limits, edit an INI value in place, drive a prompt through
  `pty`. Every example must run; add a test that extracts and `kuu check`s
  them, as `test/cases/check.lua` does for `docs/adopting.md`.
- **The PowerShell map complete:** every module has its rows.
- **`make gate`:** the suite, `analyze`, `fuzz`, and `soak` as one target,
  and `publish` depends on it. Add a sanitizer build: MSYS2's CLANG64
  packages fetched by hash into `.tools/msys2/clang64` (record the pins in
  `docs/toolchain.md` as the ucrt64 ones are), a `make asan` target
  building a test-only `build/kuu-asan.exe` with `-fsanitize=address` and
  running the suite with it. It need not be part of `gate` if it is slow;
  it must be part of the release checklist in `docs/toolchain.md`.
- **Fuzz corpus:** extend `test/fixtures/parser_fuzz.lua` to `csv.decode`,
  `ini.decode` and `ini.set`, `json.decode`, and registry key text.
